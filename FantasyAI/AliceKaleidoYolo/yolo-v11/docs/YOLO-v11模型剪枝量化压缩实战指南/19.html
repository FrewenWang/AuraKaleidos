第19章：模型压缩效果评估体系：mAP、FPS、模型大小、内存占用、功耗评估

模型压缩做完了，效果好不好？

这个问题，我几乎每次做项目都会被问到。说实话，光看模型变小了没用，得有一套完整的评估体系。今天我就把这套体系掰开揉碎了讲给你听。

19.1 评估体系总览

我个人习惯把评估指标分成四类：

  • 精度指标：mAP，看模型准不准
  • 速度指标：FPS，看模型快不快
  • 资源指标：模型大小、内存占用，看模型瘦不瘦
  • 功耗指标：实际部署时的能耗

你想想看，这四类缺一不可。我在项目中遇到过，有人只盯着模型大小，结果剪枝后精度掉得一塌糊涂，部署上去根本不能用。

核心原则：评估不是选最优，而是找平衡。精度、速度、资源、功耗，四者之间需要trade-off。

19.2 mAP：精度评估

mAP，全称mean Average Precision。说白了，就是看模型检测得准不准。

我建议你关注两个值：

  • mAP@0.5：IoU阈值0.5时的平均精度，宽松标准
  • mAP@0.5:0.95：IoU从0.5到0.95取平均，严格标准

压缩后怎么测？代码很简单：

# 使用YOLOv11官方评估脚本
from ultralytics import YOLO

# 加载压缩后的模型
model = YOLO('compressed_model.pt')

# 在验证集上评估
results = model.val(data='coco128.yaml',
                    imgsz=640,
                    batch=16,
                    conf=0.001,
                    iou=0.6)

# 打印mAP
print(f"mAP@0.5: {results.box.map50:.4f}")
print(f"mAP@0.5:0.95: {results.box.map:.4f}")

我的经验：压缩后mAP下降控制在1%以内算优秀，2%以内可接受。超过3%就要重新调整剪枝或量化策略了。

19.3 FPS：速度评估

FPS，每秒处理帧数。这个指标直接决定了你的模型能不能跑在实时场景里。

我曾经在安防项目里吃过亏——模型剪枝后精度还行，但FPS死活上不去。后来发现是量化后的算子没有硬件加速支持。

测FPS的正确姿势：

import time
import torch

def measure_fps(model, device, input_size=(1, 3, 640, 640), warmup=50, runs=200):
    model.to(device)
    model.eval()

    dummy_input = torch.randn(input_size).to(device)

    # 预热
    for _ in range(warmup):
        _ = model(dummy_input)

    # 正式测试
    torch.cuda.synchronize()
    start = time.time()
    for _ in range(runs):
        _ = model(dummy_input)
    torch.cuda.synchronize()
    end = time.time()

    fps = runs / (end - start)
    return fps

# 使用示例
fps = measure_fps(model, device='cuda:0')
print(f"FPS: {fps:.2f}")

注意：测FPS时一定要做warmup，否则第一次推理的CUDA初始化时间会严重拉低结果。我见过有人没做warmup，测出来的FPS只有实际的一半。

19.4 模型大小与内存占用

模型大小看文件体积，内存占用看运行时消耗。这两个指标经常被混淆。

指标 含义 测量方式 压缩目标
模型大小 模型文件存储体积 os.path.getsize() 减少50%-80%
显存占用 推理时GPU显存消耗 torch.cuda.memory_allocated() 减少30%-60%
内存占用 推理时CPU内存消耗 psutil.Process().memory_info() 减少20%-50%

测量代码：

import os
import torch
import psutil

# 模型大小
model_size = os.path.getsize('compressed_model.pt') / 1024 / 1024
print(f"模型大小: {model_size:.2f} MB")

# 显存占用
dummy_input = torch.randn(1, 3, 640, 640).cuda()
_ = model(dummy_input)
gpu_memory = torch.cuda.memory_allocated() / 1024 / 1024
print(f"显存占用: {gpu_memory:.2f} MB")

# 内存占用
process = psutil.Process()
cpu_memory = process.memory_info().rss / 1024 / 1024
print(f"内存占用: {cpu_memory:.2f} MB")

19.5 功耗评估

功耗这块，说实话很多做算法的人容易忽略。但做嵌入式部署时，这往往是瓶颈。

我建议用两种方式评估：

  • 软件估算：通过计算FLOPs和内存访问次数，估算理论功耗
  • 硬件实测：用功率计或板载传感器直接测量

软件估算的简单方法：

from thop import profile

# 计算FLOPs和参数量
flops, params = profile(model, inputs=(dummy_input,))
print(f"FLOPs: {flops/1e9:.2f} G")
print(f"Params: {params/1e6:.2f} M")

# 经验公式：功耗 ≈ FLOPs × 单位能耗
# 以Jetson Nano为例，单位能耗约 0.5 mJ/GFLOP
power_estimate = flops / 1e9 * 0.5  # mW
print(f"估算功耗: {power_estimate:.2f} mW")

避坑指南：我曾经用软件估算的功耗和实际差了30%。原因是没考虑内存带宽的消耗。建议软件估算只做参考，最终以硬件实测为准。

19.6 综合评估报告模板

每次做完压缩，我都会出一份评估报告。这里给你一个模板：

========================================
YOLOv11模型压缩评估报告
========================================

【基本信息】
原始模型: yolov11n.pt
压缩方法: 结构化剪枝 + INT8量化
压缩比例: 60%

【精度指标】
mAP@0.5:  原始 0.723 → 压缩后 0.711 (-1.66%)
mAP@0.5:0.95: 原始 0.512 → 压缩后 0.498 (-2.73%)

【速度指标】
FPS (GPU): 原始 142 → 压缩后 268 (+88.7%)
FPS (CPU): 原始 23 → 压缩后 41 (+78.3%)

【资源指标】
模型大小: 原始 18.5MB → 压缩后 4.7MB (-74.6%)
显存占用: 原始 1.2GB → 压缩后 0.6GB (-50.0%)

【功耗指标】
GPU功耗: 原始 15.2W → 压缩后 8.7W (-42.8%)

【结论】
压缩效果优秀，精度损失在可接受范围内，
速度和资源指标提升显著，适合边缘端部署。
========================================

嗯，这套评估体系我用了好几年。每次压缩完，把这五个指标跑一遍，心里就有底了。记住，没有完美的压缩，只有最适合你场景的平衡点。

最后说一句：评估不是终点，而是迭代的起点。根据评估结果调整压缩策略，反复优化，才能找到最优解。
