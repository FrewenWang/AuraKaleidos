第26章：云端部署实战

模型剪枝量化完了，本地跑得飞快。

然后呢？

不上线等于白干。我见过太多团队，模型在笔记本上精度99%，一上生产环境就崩。说白了，部署才是真正见真章的地方。

这一章，咱们聊聊云端部署的几种主流方案。AWS SageMaker、阿里云PAI、Docker容器化、弹性伸缩。我会把我在生产环境踩过的坑，一个一个说清楚。

26.1 AWS SageMaker部署

SageMaker是我个人比较喜欢的方案。为什么？因为它把训练、调优、部署全串起来了。你不需要自己搭推理服务器，也不用操心负载均衡。

部署一个剪枝后的YOLOv11模型，大概分三步：

  1. 打包模型：把.pt或.onnx文件打成tar.gz
  2. 写推理脚本：定义输入输出格式
  3. 创建Endpoint：指定实例类型和数量

我给你们看一个我常用的推理脚本模板：

import torch
import json
import numpy as np
from yolov11 import YOLO

def model_fn(model_dir):
    model = YOLO(f"{model_dir}/yolov11_pruned.pt")
    model.eval()
    return model

def predict_fn(input_data, model):
    images = input_data['images']
    results = model(images)
    return results

def input_fn(request_body, request_content_type):
    if request_content_type == 'application/json':
        return json.loads(request_body)
    raise ValueError("Unsupported content type")

这里有个坑，我曾经踩过：模型文件路径。SageMaker会把模型文件解压到/opt/ml/model/目录下。你如果写死了本地路径，部署上去肯定报错。嗯，这个我吃过亏。

我的建议：用环境变量SM_MODEL_DIR来获取模型路径，别写死。

26.2 阿里云PAI部署

如果你在国内做项目，阿里云PAI可能是更实际的选择。PAI的EAS服务，专门做模型在线推理。

PAI部署有个好处：自动优化。你上传模型，它会自动做一次量化加速。对于我们已经剪枝过的模型，效果更明显。

部署流程：

  • 在PAI控制台创建模型服务
  • 上传模型文件（支持onnx、pmml、pytorch）
  • 配置资源规格（我一般选ecs.g6.xlarge起步）
  • 设置弹性伸缩策略

我记得有一次，客户要求延迟低于50ms。本地测试没问题，一上PAI就超时。查了半天，发现是数据预处理太慢。图像解码、resize这些操作，在CPU上跑，拖了后腿。

解决方案？把预处理也搬到GPU上。用torchvision的transforms，一步到位。

注意：PAI的免费额度有限，生产环境记得开按量付费。我曾经忘了关实例，一晚上跑了三千多块。

26.3 Docker容器化

不管用哪个云平台，Docker容器化都是必须的。为什么？因为环境一致性。

你想想看，本地Python 3.10，服务器Python 3.6，CUDA版本还不一样。模型能跑才怪。

我一般这么写Dockerfile：

FROM pytorch/pytorch:2.0.1-cuda11.7-cudnn8-runtime

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY model/ ./model/
COPY app.py .

EXPOSE 8080

CMD ["python", "app.py"]

这里有个细节：基础镜像选择。别用full版本，太大了。runtime版本就够了，少了300MB。我刚开始做容器化时，镜像动不动就2GB，上传一次等十分钟。后来改用slim版本，快多了。

构建命令：

docker build -t yolov11-serving:latest .
docker tag yolov11-serving:latest your-registry/yolov11-serving:latest
docker push your-registry/yolov11-serving:latest

26.4 弹性伸缩

流量是波动的。白天上班时间请求多，半夜几乎没人。如果一直开着10台机器，成本扛不住。

弹性伸缩就是干这个的。说白了，根据CPU使用率或请求数，自动加减机器。

在SageMaker里配置：

  • 最小实例数：1（保证基础服务）
  • 最大实例数：10（应对突发流量）
  • 扩缩容策略：CPU超过70%扩容，低于30%缩容

在阿里云PAI里类似，叫自动弹性。我建议设置一个冷却时间，比如300秒。防止频繁扩缩容，造成抖动。

我曾经遇到过一个情况：双十一流量暴增，弹性伸缩没来得及反应，服务直接挂了。后来加了预热策略——提前半小时预扩容。嗯，这个经验值钱。

核心要点：弹性伸缩不是万能的。它适合应对可预测的流量波动。如果是突发的尖峰流量，建议配合限流和降级策略一起用。

避坑指南

最后，分享几个我亲身踩过的坑：

  • 模型加载慢：第一次请求可能要等5秒。解决方案：用warmup，启动时先跑一次推理。
  • GPU显存泄漏：每次推理完没释放显存，跑几天就OOM。加个torch.cuda.empty_cache()。
  • 日志太多：每个请求都打印完整结果，磁盘很快写满。只记录关键指标，比如延迟和错误码。
  • 版本管理混乱：模型更新了，但线上还是旧版本。用模型版本号，每次部署都打tag。

嗯，云端部署这件事，说难不难，说简单也不简单。关键是每个环节都别偷懒。容器化、弹性伸缩、监控告警，一个都不能少。

你按照这个流程走一遍，基本不会出大问题。
