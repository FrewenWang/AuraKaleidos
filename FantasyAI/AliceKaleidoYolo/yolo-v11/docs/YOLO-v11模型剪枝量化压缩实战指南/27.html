第二十七章：模型压缩项目实战——目标检测项目全流程

说实话，走到这一步，你才算真正摸到了模型压缩的“硬骨头”。

前面我们聊了剪枝、量化、蒸馏，都是拆开讲的。但实际项目中，没人会给你一个干净的模型让你慢慢调。你拿到的，往往是一个跑在GPU上、精度还行但速度拉胯的检测模型。老板只丢一句话：“把它塞进边缘设备，帧率要翻倍。”

嗯，这时候就需要一套完整的实战流程了。从训练到压缩，再到部署，每一步都可能踩坑。我今天就带你走一遍这个全流程，把我踩过的坑、总结的经验，一股脑倒给你。

核心目标：将一个YOLOv11目标检测模型，从原始训练状态，经过剪枝+量化联合压缩，最终部署到边缘设备（如Jetson Nano），在保证mAP下降不超过3%的前提下，推理速度提升2-3倍。

一、项目全流程总览

先看一张图，把整个流程串起来。我习惯在动手前先画个框架，不然容易迷失方向。

说白了，这五个阶段是环环相扣的。你跳过一个，后面就得加倍还债。我个人习惯在阶段1就把baseline的精度和速度记录清楚，后面每一步压缩，都要跟这个baseline对比。

二、阶段1：训练一个可靠的Baseline

很多人一上来就想着怎么压缩，结果发现原始模型本身就有问题。我踩过这个坑——训练时没调好学习率，模型收敛得稀烂，剪枝后精度直接崩了。

所以第一步，老老实实训练一个YOLOv11 baseline。这里有几个关键点：

  • 数据集准备：COCO或自定义数据集，确保标注质量。我建议至少检查200张图的标注，别信“标注完就能用”这种鬼话。
  • 超参数设置：batch size=16，初始学习率0.01，使用余弦退火调度。epoch数设300，但早停法要开着。
  • 评估指标：记录mAP@0.5:0.95、mAP@0.5、FPS（在目标设备上测）。

我的小技巧：训练完成后，保存一份FP32的权重文件，同时导出ONNX格式。后面所有压缩操作都基于这个ONNX模型，避免反复从PyTorch导出。

三、阶段2：结构化剪枝——砍掉冗余通道

剪枝这一步，说白了就是“瘦身”。YOLOv11的C2f模块里有很多通道，有些通道对最终检测结果贡献很小，砍掉它们不会影响精度。

我推荐用结构化剪枝，按通道维度剪。具体做法：

  1. 对每个卷积层计算BN层的gamma值，按绝对值排序。
  2. 设定剪枝率（比如30%），砍掉gamma值最小的那些通道。
  3. 重新训练（微调）50-100个epoch，恢复精度。
# 伪代码示例：基于BN gamma的通道剪枝
import torch
import torch.nn.utils.prune as prune

def structured_prune(model, prune_ratio=0.3):
    for name, module in model.named_modules():
        if isinstance(module, torch.nn.BatchNorm2d):
            # 获取gamma值
            gamma = module.weight.data.abs()
            # 计算阈值
            threshold = torch.quantile(gamma, prune_ratio)
            # 生成掩码
            mask = gamma > threshold
            # 应用剪枝
            prune.custom_from_mask(module, name='weight', mask=mask)
    return model

注意：剪枝率不是越高越好。我曾经试过50%剪枝率，结果mAP掉了8个点，微调都救不回来。建议从20%开始，每次增加5%，观察精度变化。

四、阶段3：量化——从FP32到INT8

剪枝完，模型参数少了，但计算精度还是FP32。要想真正提速，得做量化。

量化有两种主流方式：

方法 优点 缺点 适用场景
PTQ（训练后量化） 速度快，无需重新训练 精度损失可能较大 对精度要求不高的场景
QAT（量化感知训练） 精度损失小，通常<1% 需要重新训练，耗时 对精度敏感的场景

我个人习惯先用PTQ试试水。如果mAP下降超过2%，再上QAT。你想想看，QAT要重新训练，时间成本高，能省则省。

# PTQ量化示例（使用TensorRT）
import tensorrt as trt

def build_int8_engine(onnx_path, calib_data):
    TRT_LOGGER = trt.Logger(trt.Logger.WARNING)
    builder = trt.Builder(TRT_LOGGER)
    network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, TRT_LOGGER)

    with open(onnx_path, 'rb') as f:
        parser.parse(f.read())

    config = builder.create_builder_config()
    config.set_flag(trt.BuilderFlag.INT8)
    config.int8_calibrator = MyCalibrator(calib_data)

    engine = builder.build_engine(network, config)
    return engine

避坑指南：量化时校准数据集的选择很关键。我曾经只用100张图做校准，结果部署后检测框全偏了。后来改用500张，覆盖各种光照和角度，精度才稳住。

五、阶段4：部署到边缘设备

模型压缩完了，得让它跑起来。这里以Jetson Nano为例，部署TensorRT引擎。

部署流程：

  • 将量化后的模型导出为TensorRT engine文件。
  • 编写推理代码，加载engine，处理输入输出。
  • 优化数据预处理（比如用CUDA加速resize和归一化）。
# TensorRT推理代码片段
import tensorrt as trt
import pycuda.driver as cuda

def inference(engine, input_data):
    context = engine.create_execution_context()

    # 分配GPU内存
    d_input = cuda.mem_alloc(input_data.nbytes)
    d_output = cuda.mem_alloc(output_size)

    # 拷贝数据到GPU
    cuda.memcpy_htod(d_input, input_data)

    # 执行推理
    context.execute_v2([int(d_input), int(d_output)])

    # 拷贝结果回CPU
    cuda.memcpy_dtoh(output_data, d_output)
    return output_data

六、阶段5：效果验证与优化

部署完了，别急着庆祝。先跑一遍验证集，看看精度和速度。

我一般会做三件事：

  1. 精度对比：把压缩后的模型和baseline在同一个验证集上跑，对比mAP。如果下降超过3%，就得回退调整剪枝率或量化方式。
  2. 速度测试：在目标设备上测FPS，至少跑1000帧取平均值。注意要排除前几帧的预热时间。
  3. 可视化检查：随机抽100张图，肉眼对比检测框。有时候mAP没掉，但某些类别检测不准，肉眼一看就发现了。

实战结果参考：我做过的一个项目，YOLOv11s在Jetson Nano上，原始FP32模型FPS=15，mAP=42.5%。经过30%剪枝+INT8量化后，FPS=42，mAP=41.2%。速度提升2.8倍，精度只降了1.3%。这个结果，老板是满意的。

七、优化技巧与避坑指南

最后，分享几个我实战中总结的优化技巧：

  • 剪枝和量化的顺序：先剪枝后量化。如果先量化再剪枝，量化后的低精度权重会让剪枝的排序不准。
  • 微调策略：剪枝后的微调，学习率要调低，一般是原始学习率的1/10。我用0.001起步，每20个epoch衰减一次。
  • 校准数据多样性：量化校准集要包含不同场景、光照、目标大小的图片。我吃过亏，只用白天图片校准，晚上场景直接崩了。
  • TensorRT版本兼容：不同版本的TensorRT对算子支持不一样。部署前一定要确认目标设备上的TensorRT版本，否则engine可能跑不起来。

曾经踩过的坑：有一次我剪枝后直接量化，没做微调，结果mAP掉了5个点。后来老老实实加了50个epoch的微调，精度才回来。记住，剪枝后的微调不是可选项，是必选项。

好了，整个项目全流程就是这样。从训练到压缩，再到部署验证，每一步都有讲究。你按照这个流程走一遍，基本不会出大问题。如果遇到精度掉得厉害，别慌，回头检查剪枝率、量化校准集、微调参数，总能找到原因。

动手试试吧，把理论变成实战，才是真正的掌握。
